# ADR-015: Asynchronous Visibility

Status: Accepted
Date: 2026-09-05

## Decision

Favor frame responsiveness over immediate visibility. Compute existing padded frustum eligibility on one dedicated worker using exclusively owned value snapshots. Keep one running job, one replaceable pending request, one result slot and one main-thread application batch. No scene objects, terrain access, recorder state or gameplay mutations cross the worker boundary.

Soft camera changes do not cancel running work. Adopt monotonically newer completions within the current renderer epoch, even when the camera has moved again, and finish their application before taking another soft result. World/renderer/streaming resets, level changes, camera identity changes and viewport identity/size changes invalidate all older work and partial batches without rolling back actual state. Cancellation is cooperative at 256-candidate boundaries. Only teardown joins the worker.

The main-thread pump runs once per Main frame, including menus/loading, with a shared cooperative 1 ms/2048-step allowance for application and thread-start-failure fallback. Stable coordinate slots bound reconciliation without copying whole dictionaries. Effective eligibility includes missing/empty mesh coordinates and is distinct from actual shown nodes. All mesh-install/hide/removal paths maintain shown state. Additions precede removals; partial views and latency remain explicit diagnostics.

## Amendment (2026-10-05): delta application

F1 captures measured 170-210 ms visibility lag during fast camera pans: chunks were loaded and meshed but remained hidden while each accepted view scanned roughly 1.7k-7k accepted and eligible coordinates under the 1 ms pump (about 750 steps per frame), taking 5-14 frames. Typical frame-to-frame changes are only a few hundred coordinates. Each request now carries the most recently adopted `base_sequence`. The worker retains the accepted dictionaries from the last four published results in the current epoch and computes entering/exiting coordinates off the scheduler mutex. The main thread applies additions before removals, one coordinate per pump step. It uses a delta only when the result's base matches the last fully applied sequence in the same epoch and eligibility is clean, with no pending reconcile or initial-node scan; otherwise the existing full scan applies. Thread-start failure deliberately keeps the incremental kernel and full-scan application, so it never performs an unbudgeted diff on the main thread. The worker does not mutate published accepted sets after handoff, and the history is discarded on epoch invalidation.

## Consequences

Visibility can lag during motion and cached level changes. Existing terrain/mesh loading remains, but visibility introduces no new loading-screen gate. Broad cave coverage, padding, save formats and normal streaming budgets are unchanged. Startup failure falls back to the same incremental kernel, never a full synchronous scan. Budgeting cannot bound every engine call, allocation or operating-system delay; this is not a zero-stutter guarantee.

Worker completion/cancellation accounting is distinct from main-thread pump cost and request-to-applied age. Capture epochs exclude earlier recordings without changing scheduling. Headless kernel-oracle, mailbox, partial-application, lifecycle and legacy validators establish correctness, not GPU/visual acceptance or controlled performance improvement.

## Guardrails

- `render_zone_cull_scheduler.gd` and `render_zone_cull_kernel.gd`: value-only ownership and bounded scheduling.
- `world_renderer_visibility.gd` and `stable_coord_slots.gd`: effective/shown state and budgeted reconciliation.
- `validate_cull_kernel_rows.gd`: the row-interval kernel against the per-cell culler on random boxes and plane sets.
- `validate_render_zone_cull_scheduler.gd` and `validate_async_visibility.gd`: thread barriers, stale results, lifecycle and frame-pump contracts.

Follow-up (2026-10-05): requests are submitted every frame while the camera moves (a newer request replaces the pending one). With publications every ~23 ms, the four-entry history evicted the main thread's base before its next job finished, so 105 of 169 applications fell back to full scans. A first fix pinned the submit-time base, but with a request every frame some job is always in flight with a base older than the next adopted result (481 of 606 applications were still full). The main thread now reports each adoption (`note_adopted`); the worker pins that result and diffs every completing job against it, and the main thread accepts a delta when `delta_base_sequence` equals the last applied sequence. The kernel tests normalized planes (identical results to FrustumCuller, ~40% faster). Symmetric speed-scaled padding was tried and rejected (6 chunks grew the accepted set to ~9.9k); instead a job may carry `lead_planes`, the frustum translated by the smoothed pan velocity times 0.15 s (capped at 48 units), and a chunk is accepted when it is inside either frustum. Base padding is unchanged.
Review hardening (2026-10-09): a one-frame camera move above 64 units (Locate, load, level change) is a teleport and resets the smoothed lead instead of seeding it; pan speed is clamped to the speed the 48-unit lead can represent; stream reset clears the lead. The render-zone key includes whether a lead is active, so the view is re-requested once the lead decays to zero and the look-ahead chunks are trimmed at rest. `lead_planes` are validated at submit like `planes`.

Debug comparison modes (2026-10-09, debug builds via the F7 Rendering panel; runtime only): `area` submits the render box with no frustum planes so every meshed chunk in the box is shown and Godot's own culling skips off-screen ones; `sync` culls and applies the whole view on the main thread in the request call, unbudgeted. Both exist to measure this ADR's async design against its alternatives and are not shipping modes. A depth limit (top N chunk layers), freeze, look-ahead on/off and lead seconds, and refresh cadence are also switchable. A void meter (on-screen chunks in the top two render layers that have geometry but are hidden) samples at 20 Hz while the panel is open and is included in F1 visibility snapshots.

Row intervals (2026-11-11): the kernel no longer tests every cell. Along one Z row each plane's test is monotone, in floating point as well as exactly, so a row's accepted cells form one interval per frustum; the kernel finds it by bisection with the same plane test and counts a row with no accepted cell in one step when the budget covers it. Results, order, candidate counts and the step budget are unchanged. Measured on a 512 world with `tools/perf_capture.gd` (about 37,000 candidates per job): job time 65.5 ms to 10.7 ms, request-to-shown latency at a 60 blocks/s pan about 80 ms to 17.5 ms, and the void meter went from 27 of 191 samples showing hidden on-screen chunks to none. At 200 blocks/s a void still appears after sharp direction changes (13 of 190 samples, up to 5 chunks); the look-ahead only leads in the direction of travel.

Application order (2026-11-11): additions are applied top chunk layer first, in both full and delta mode. The kernel lists coordinates bottom layer up and the player looks at the top of the slice, so under the per-frame budget the visible layers used to be shown last. Additions still precede removals. Measured with a shuttle pan (direction reversal every 0.4 s) at 350 blocks/s, three runs each: samples with hidden on-screen chunks 35/32/27 of 193 before and 23/25/26 after. What remains at that speed is application volume: a reversal swings the look-ahead frustum, a result can carry 6,000 to 19,000 steps, most of them for buried chunks with no node, and the next result waits until they are applied.

Pan limiter (2026-11-11): every pan (keys, mouse drag, scripted) goes through `MainCameraController.pan_by`, which asks `WorldRenderer.limit_camera_pan` how far it may go. A view accepts every chunk within the frustum padding (8 blocks) of its frustum, and its candidate box is the screen footprint plus one chunk, so while the camera is within that padding of a view's camera origin on each axis, everything that can be drawn on screen was accepted by that view. The limiter keeps the camera within 7 blocks (padding minus one) per axis of every view that decides what is shown: the applied view, the view being applied, and the views that can still be adopted (published result, running job, pending request). It never pulls the camera back, and it leaves an axis alone when the camera is already far outside (a jump) or the views cannot be satisfied together. Jumps, zoom and level changes do not use it. `render_debug.pan_limit` (F7 panel, on by default) turns it off; it only applies in `async` mode and not while frozen. The cost is pan speed: the camera advances about 7 blocks per applied view. Measured on the 512 world with a shuttle pan, limiter on: 60 blocks/s requested, 100% travelled, 0 limited steps; 200 requested, 92% travelled; 350 requested, 72% travelled (about 250 blocks/s effective); 1,000 requested, 30% travelled (about 300 blocks/s effective). Void samples were 0 of 192 to 194 in every limiter-on run, against 12 of 192 (up to 10 chunks hidden, longest 108 ms) at 350 blocks/s with it off. `tools/validate_pan_limiter.gd` checks the geometric claim against `FrustumCuller`, the clamp rule and the anchors; the zero-void result itself is a windowed capture, not a headless validator.

Void meter correction (2026-11-11): the meter tested each chunk's whole bounding box against the view. The terrain shader discards blocks above the cut (`block y > top_render_y`), so a top-layer chunk at the near screen edge could reach the view only with the part of its box above the cut, where nothing is drawn, and be counted as missing terrain. Such chunks lie outside the candidate box of the applied view, which is built from the footprint of the drawn height range, so no view would ever show them in time. The meter now clips the top layer's box one block above the cut (`WorldRenderer.is_drawn_part_in_view`). Void counts recorded before this date include those chunks: the same 350 blocks/s shuttle pan with the limiter off read 35 of 191 samples with the old meter and 12 of 192 with the corrected one.

View-driven mesh requests (2026-11-11): in wide worlds (ADR-022) terrain is meshed on demand, and the only thing asking for meshes during a pan was the streaming queue. That queue restarts whenever its bounds change (921 of 1,173 frames in a 60 blocks/s pan) and works layer by layer through off-screen buffer chunks as well, so on ground that had never been meshed it built thousands of off-screen meshes while on-screen chunks were never requested: 50 to 60% of the frame was background at 60 blocks/s and up to 84% at 350, and it could stay that way at rest. `ViewMeshRequester` (`scripts/rendering/view_mesh_requester.gd`) now serves the newest adopted view directly. It walks the view's accepted coordinates from the top layer down and queues, at high priority, every chunk that can show something and is not built. A chunk can show something only at or above its column's visible floor: the lowest block seen from above through the cut, in that column or a face neighbour (sampled every second cell, remembered per column, forgotten when the terrain there changes or the cut moves). Chunks above the cut and buried chunks are never requested, and the walk stops at the first layer below every floor it has met. A view still never creates or generates terrain: chunks with no blocks yet are skipped and are meshed when generation delivers them, as before. The backlog is capped at 192 chunks. The streaming queue is unchanged and still fills the buffer. When every needed chunk of a view is built the view is reported meshed; a view that makes no progress for 0.75 s is reported anyway so a chunk that cannot be built cannot hold the camera. `render_debug.view_meshes` (F7 panel, on by default) turns the requester off. Cost: about 0.2 ms of main thread per frame while panning, 0.9 ms worst case. Known gaps: a one-block shaft between sampled cells, and the wall at the map's near edge, are left to the streaming queue.

Pan limiter and meshes (2026-11-11): the limiter gains one more anchor, the camera origin of the last view reported meshed, so the camera cannot outrun terrain that has a mesh either. After a jump that anchor is far away and does not bind until a view at the new place is meshed. Measured with the pixel probe (`tools/perf_capture.gd --void-pixels=1`, which sets the background to magenta and counts background pixels inside the world on the rendered frame) on never-visited ground of the 512 world: background pixels were zero in every sample at 60, 350 and 1,000 blocks/s requested, against up to 60% of the frame with the requester off. Pan travelled: 100% at 60 blocks/s, 73 to 79% at 350 (about 260 to 275 blocks/s), 47% at 1,000 (about 465 blocks/s). With the requester on and the limiter off the same 350 blocks/s pan showed background in 1 of 78 samples (0.5% of the frame). The chunk-state void meter cannot see unbuilt chunks; the pixel probe is the acceptance test for void. `tools/validate_view_mesh_requester.gd` covers the request rules headless.
